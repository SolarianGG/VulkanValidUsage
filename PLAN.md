# Vulkan RAG vs Model Memory: план эксперимента

## 1. Цель и гипотезы

Сравнить, насколько точно LLM отвечает на вопросы о правилах Valid Usage в Vulkan:
- **closed-book**: модель отвечает только по своей памяти;
- **RAG** с разными стратегиями retrieval: BM25, Dense, гибрид RRF, rerank, HyDE и query rewriting;
- **oracle**: в контекст подан gold-чанк. Это верхняя граница, она отделяет ошибки retrieval от ошибок генерации.

Гипотезы (операционализация и критерии в §7.5):
- **H1.** RAG лучше closed-book. Сильнее всего разрыв на свежих и редких правилах (страты `recent`, `ext_niche`).
- **H2.** Гибрид (RRF) лучше по Recall@k, чем BM25 и Dense по отдельности. Причина: идентификаторы Vulkan (`vkCmdDraw`, `VK_IMAGE_LAYOUT_*`) хорошо ловит BM25, а перефразированную семантику лучше ловит Dense. Особенно это должно проявиться на описательных вопросах без идентификаторов (проверяется как взаимодействие «конфигурация × стиль» на парных вопросах, §4 Этап 3).
- **H3.** Reranker повышает Recall@5 и итоговую точность при умеренной цене по задержке.
- **H4.** Небольшая локальная модель (qwen3.5:9b) с RAG не хуже крупной модели из OpenRouter в режиме closed-book (non-inferiority). Вывод относится только к выбранной remote-модели и не обобщается на «крупные модели» вообще.
- **H5.** Для OpenRouter-ответчика RAG повышает стоимость одного вопроса, потому что растут входные токены, но снижает стоимость одного правильного ответа по сравнению с closed-book.

| Результат | воспроизводимый CLI-пайплайн и отчёт (notebook и markdown) с таблицами и графиками |

## 4. Этапы

### Этап 0. Окружение
- `uv`. Основные пакеты: `bm25s`, `sentence-transformers`, `FlagEmbedding`, `faiss-cpu`, `ollama`, `httpx`/`openai` (для OpenRouter), `typer`, `pydantic`, `pandas`, `matplotlib`, `scipy`, `statsmodels`, `beautifulsoup4`/`lxml`.
- Docker Desktop (WSL2) для сборки spec: клон для сборки лежит в Docker-volume (ext4 внутри VM), не в `/mnt/c`. Python и Ollama работают нативно в Windows (§9.1). GPU не делим между двумя рантаймами без необходимости.
- Ollama: `qwen3.5-9b-text` (§2), `num_ctx` из конфига **в каждом запросе** (по умолчанию в Ollama 2–4k), `num_predict` задан явно (лимит выходных токенов, в конфиге), `temperature=0`, `presence_penalty=0`, `think=false`.
  - Проверить через `ollama ps`, что модель на 100% GPU. CPU offload недопустим, он испортит задержку. *(Проверено: 100% GPU, 33/33 слоя; 546 MB входных эмбеддингов llama.cpp всегда держит на CPU, это не offload. Если `inference compute` в логе Ollama показывает `library=cpu`, установка повреждена — переустановить.)*
  - Проверить, что в ответах нет `<think>` (шаблон может игнорировать `think=false`), включая пустой `<think></think>`. Это касается и генерации, и rewrite/HyDE.
  - Проверить, что после `keep_alive=0` VRAM реально освобождена (`nvidia-smi`), а не только модель пропала из `ollama ps`.
  - Измерить свободную VRAM с учётом того, что занимает Windows/дисплей. *(Проверено: Windows 1.2–1.9 GB; с qwen занято 6.6 из 8 GB. bge-m3 + reranker рядом с qwen, вероятно, не помещаются — уточнить после установки torch.)*
- `.env` с `OPENROUTER_API_KEY` (в `.gitignore`). Жёсткий лимит расходов выставить **на самом ключе** в OpenRouter, а не только в конфиге.
- Проверить, что OpenRouter возвращает `usage.cost`, фактический `model` и провайдера (при необходимости включить usage accounting или запрашивать `/api/v1/generation`). Проверить, что выбранный провайдер поддерживает `response_format` с JSON schema (`require_parameters: true`) и учитывает ли reasoning-модель `temperature`.
- Git: `core.autocrlf=false` для клонов (иначе `\r` ломает регулярки), клон Vulkan-Docs **без** `--depth`.
- Unit-тесты токенизатора BM25 и нормализации **на реальном входе** (фрагменты собранного HTML и текста из `validusage.json` с `<code>`, `<a>`, latexmath, а не на asciidoc-макросах вроде `pname:`): `VK_IMAGE_LAYOUT_*`, `VkPhysicalDeviceVulkan13Features`, `vkCmdBindPipeline`, `vkCmdBeginRenderingKHR` (алиас), `1.3`.
- Ноутбук: режим питания «максимальная производительность», работа от сети. Для фазы L фиксируем это в manifest (троттлинг искажает задержку).

### Этап 1. Ingest и корпус
1. Клонировать Vulkan-Docs и Vulkan-Headers на одном и том же теге.
2. Собрать spec штатно, со всеми расширениями, в Docker: single-page HTML и `validusage.json` (`vkrag spec build`). Provisional-расширения входят в `-spec all` и в json (проверено). Так решаются `include::`, атрибуты (`{refpage}`), `ifdef::`/`endif::` и шаблоны `commonvalidity` для текста. Сырой adoc используем для условий VU (п. 4а) и для git-датирования (Этап 2).
3. Сверить набор VUID собранного json с `registry/validusage.json` из Vulkan-Headers того же тега. Расхождения записать в `coverage_report.json`. *(v1.4.366: совпадение полное, 27 429 VUID.)*
4. Разобрать `validusage.json` (фактический формат v1.4.366 — schema v2: `validation → entity → "core" → [{vuid, text, page}]`):
   - VUID → {текст, сущность, параметр, explicit или implicit, `page`}. **Сущность берётся из ключа json**, имя в самом VUID может быть старым (алиас до промоушена, 15 случаев: `VUID-VkBlitImageInfo2KHR-…` под ключом `VkBlitImageInfo2`) и хранится как `vuid_entity`;
   - **explicit/implicit определяется по суффиксу VUID**: у explicit числовой суффикс, у implicit текстовый (16 видов: `parameter`, `sType`, `pNext`, `recording`, `cmdpool`, `videocoding`, `arraylength`, `parent`, `suspended`, `commonparent`, `unique`, `renderpass`, `zerobitmask`, `queuecount`, `bufferlevel`, `queuetype`; у 669 нет параметра: `VUID-X-commonparent`). Неизвестные суффиксы логировать;
   - **4а. Условие расширений** — из adoc (`ingest/adoc_conditions.py`), а не из json: мини-препроцессор обходит `include::` от `vkspec.adoc` (включая `include::…[tag=…]`, в том числе самовключения файла; `{generated}/` не обходится — там нет explicit VUID), подставляет атрибуты (`{refpage}` и др.), оценивает `ifdef`/`ifndef` по атрибутам `gen/specattribs.adoc` и записывает для каждого VUID-анкера конъюнкцию активных `ifdef` в ДНФ (`conditions.py`). Грамматика: `,` — ИЛИ, `+` — И, скобок нет, И — через вложенность; одно смешанное выражение `A,B+C` трактуется как `A ∨ (B ∧ C)`. Клаузы с неопределёнными в сборке атрибутами (`hidden`, `VKSC_*`, …) отбрасываются, служебные атрибуты убираются. Имена `VK_{BASE,COMPUTE,GRAPHICS}_VERSION_x_y` сводятся к `VK_VERSION_<max>` в клаузе, `VK_VERSION_1_0` рядом с расширением убирается. *(Результат: все 20 575 explicit VUID, точное совпадение с json, 0 неразрешённых.)*;
   - текст нормализовать: убрать HTML (`<code>`, `<strong>`), сохранить текст ссылок, а целевые анкеры ссылок (`<a href="#...">`) сохранить в метаданных как `refs`. Это секции, нужные для ответа. Формулы в json — сырой TeX `\(...\)` → читаемый текст (`ceil((a+b)/c)`), в HTML — KaTeX-вёрстка без TeX-источника → линеаризация (дроби, индексы); `html.unescape`; вложенные списки → `- item`;
   - **единственный источник текста VU-чанка — `validusage.json`**. Из HTML VU-блоки вырезаются.
   - Implicit VU (автогенерируемые проверки sType/pNext/handle/recording/renderpass) **исключаем из вопросов**, но оставляем в корпусе, их текст тоже берём из json.
5. **Сущности вне `vk.xml`**: `RuntimeSpirv` (363 VU), `StandaloneSpirv` (201), 125 встроенных переменных (`Position`, `FragCoord` и т. п., 414 explicit VU). Помечаются `entity_kind = spirv|builtin|api`. В корпусе остаются. В вопросы берутся с отдельной стратой-меткой `entity_kind` (для разреза в отчёте), ограничение «≤ 3 VU на сущность» действует и для них. Для автопроверок идентификаторов используется `spirv_identifiers.txt`.
6. Разобрать собранный HTML на секции (`ingest/sections.py`):
   - refpage-секции команд, структур, enum, встроенных переменных = `div.openblock` верхнего уровня (родитель — `sectionbody`/`sectN`); идентификатор — `id` первого `div.listingblock` (C-прототип), для встроенных переменных — имя из VUID. Описательный текст непосредственно перед open-блоком приписывается к refpage, **если он ≤ 150 слов**, иначе остаётся в прозе;
   - **прозаические главы и подглавы** (synchronization, image layouts, memory model, formats, приложения): всё, что лежит прямо в `sectN`, кроме дочерних секций и refpage-блоков, потому что на них указывают `refs`. Заголовок секции без собственного текста сопоставляется с первым юнитом внутри неё (для `anchor_map`). Номера глав/приложений из заголовков убираются.
   - Блоки `Valid Usage` и `Valid Usage (Implicit)` из секции удалить. Список VUID этой секции хранится **в метаданных** (`vuids_in_section`), а не в тексте чанка.
   - Блоки `Host Synchronization` и `Command Properties` оставить в тексте секции (это источник implicit-правил про render pass и типы очередей), таблицу `Command Properties` нормализовать в читаемый текст.
   - Нормализовать таблицы, NOTE, latexmath.
7. **Алиасы**: из `vk.xml` извлечь `alias` для команд, структур и enum (`*KHR`/`*EXT` ↔ core) в `aliases.json`. Используется в BM25 (расширение запроса алиасом) и в автопроверках идентификаторов.
8. **Происхождение сущности**: из `vk.xml` (`<feature>`/`<extension>` `<require>`) для каждой API-сущности определить core-версию или расширение, а также флаги `deprecatedby`, `obsoletedby`, `promotedto`, `specialuse`, `provisional`. Условие `core` у VU **не означает** Vulkan 1.0: оно отражает только `ifdef` вокруг самого VU.
9. **Классы эквивалентности VU** (`equivalence.py`):
   - основное правило: explicit VUID с одинаковым числовым суффиксом образуют класс (в основном шаблоны `commonvalidity`: draw/dispatch/trace rays/copy);
   - объединение по **полному совпадению нормализованного текста** (без замены имени сущности на плейсхолдер — решение §10; `corpus.equiv_text_placeholder: false`) применяется **только к explicit VU**. Нечёткого сравнения нет;
   - implicit VU в классы не объединяются (иначе шаблонные «must be a valid handle» сливаются в гигантские классы);
   - класс хранится в `vuids.jsonl` как `equiv_class_id`. В отчёт идёт распределение размеров классов, 10 крупнейших классов проверяются глазами.
10. **VU-чанк** состоит из двух представлений:
    - `index_text` (для BM25, Dense, reranker): `[{entity}] [{parameter}] [{availability}]` + текст правила. Без заголовка «*buffer* must have been created with…» не имеет смысла ни для BM25, ни для Dense. `parameter = None` не выводится. `availability` — **компактная метка**: уникальные расширения и версии (`Vulkan x.y`) из условия, не больше трёх плюс «(+N more)»; для `core` — core-версия или расширения сущности. Полная ДНФ — только в метаданных (полная формула раздувала заголовок отдельных VU до 1 000+ токенов);
    - `llm_text` (для контекста LLM): тот же текст плюс `VUID`, чтобы модель могла его цитировать.
11. Метаданные чанка: `chunk_id, type (section|vu), entity, entity_kind, vuid?, equiv_class_id?, section_id, part_idx, extension?, core_version?, refs, source_anchor, vuids_in_section?`. Метаданные **не** подмешиваются в embed- и LLM-текст, кроме контекстного заголовка (и VUID в `llm_text`).
12. `chunk_id` **детерминированный**: из `source_anchor`, `part_idx` и хэша нормализованного текста (VU-чанк: из VUID). Тогда при пересборке корпуса `gold_chunk_ids` и кэши не разъезжаются.
13. Длина секционных чанков ≤ 800 токенов **по максимуму из трёх токенизаторов** (`tokens.py`, `tokenizer.json` с HF, ревизии в `coverage_report.json`): qwen (`Qwen/Qwen3.5-9B`), XLM-R (`BAAI/bge-m3`; запас под запрос, чтобы пара запрос+чанк ≤ 1024) и `answerer_remote` (`deepseek-ai/DeepSeek-V4-Flash-0731`). Ограничивает XLM-R (на идентификаторах ~2× qwen). VU-чанки не режутся; explicit VU сверх лимита нет, implicit — 2 (`pNext`-списки, усекаются эмбеддером). Разбивать по абзацам. Атомарные блоки длиннее лимита (большие таблицы, длинные списки) разбиваются по строкам/пунктам с повтором шапки таблицы. Каждая часть получает `section_id` и `part_idx`, а в текст части повторяется заголовок секции. Распределение длин по типам чанков идёт в отчёт.
14. **Проверка покрытия**: каждый explicit VUID из json сопоставлен с VU-чанком и родительской секцией. Процент несопоставленных пишется в `coverage_report.json` и в отчёт. Порог для продолжения: ≥ 99%. *(v1.4.366: 100%.)*

### Этап 2. Стратификация
**Датирование VU.** Дата VU = дата первого тега Vulkan-Docs, в котором в `validusage.json` появился VUID **с этим числовым суффиксом** (а не с этой полной строкой: при промоушене и переименованиях параметров строка меняется, например `VUID-vkCmdBeginRenderingKHR-…` → `VUID-vkCmdBeginRendering-…`). Прогоняем только теги за последние ~3 года (cutoff-даты моделей 2024+, более ранние VU заведомо «старые»), json генерируется из Headers этих тегов. Прокси «числовая часть VUID выделяется монотонно» используется только как санити-чек: номера выделяются при внутренней разработке до публикации, поэтому выбросы ожидаемы. Для implicit VU датирование не нужно.

Страты VU, по порядку приоритета (VU попадает в первую подходящую):
1. **recent**: дата VU позже `recent_cutoff_date`. Так в эту страту попадают и новые VU в core-командах 1.0 (например, правила dynamic rendering у `vkCmdDraw`). В отчёте дополнительно разрез `recent × происхождение сущности`.
2. **ext_niche**: vendor-расширения и KHR/EXT ниже порога популярности.
3. **ext_popular**: KHR/EXT с покрытием ≥ X% устройств на gpuinfo.org. Снимок в `data/external/gpuinfo_snapshot.json`: дата, фильтр платформы (по умолчанию desktop: Windows + Linux; Android отдельно не учитывается), метрика (поддержка расширения, не фичи). Promoted-расширения, которые также популярны, попадают сюда, только если условие VU требует именно расширение, а не core-версию (например, `VK_VERSION_1_3,VK_KHR_x` — это ИЛИ, такой VU идёт в `core_promoted`).
4. **core_promoted**: функциональность 1.1–1.4 (бывшие расширения).
5. **core_1_0**: исходный Vulkan 1.0.

Принадлежность к расширению или core определяется **комбинацией** условия VU (восстановленного из adoc, Этап 1, п. 4а; поле `condition` в `vuids.jsonl`) и происхождения сущности (Этап 1, п. 8).

Исключаются из вопросов (остаются в корпусе):
- implicit VU;
- VU, в условии которых есть provisional-расширение, **и** VU сущностей, которые сами определены provisional-расширением;
- VU сущностей из расширений с `obsoletedby` или `specialuse`; deprecated-расширения допускаются, но помечаются флагом.

Правила:
- `recent_cutoff_date` задаётся **для каждой модели-ответчика**. Источник даты (официальная карточка модели, документация провайдера, иначе — оценка по пробным вопросам о датированных событиях) фиксируется в конфиге. Если дата не раскрыта, это явно указывается в отчёте. Страта `recent` считается относительно более ранней из дат, а в отчёте приводится чувствительность к выбору даты. Дата среза не гарантирует, что расширения нет в обучающих данных, это идёт в ограничения.
- Флаг `text_changed_recently` ставится для VU, **нормализованный** текст которых (без разметки, ссылок и переносов) за последние N тегов изменился сильнее порога (нормализованное расстояние Левенштейна > 0.1 или изменилось множество идентификаторов). Это риск того, что модель ответит по старому spec. Такие VU разбираются отдельно.

Выборка ~400 VU: целевые 80 на страту, seed фиксирован, все входные списки сортируются явно перед сэмплированием (порядок обхода json не должен влиять на выборку).
- Не больше 3 VU на одну сущность и **не больше одного VU на класс эквивалентности**.
- Если в страте меньше 80 подходящих VU, берём все. Недостачу не перераспределяем.
- **Веса страт** для взвешенного агрегата = доля страты среди всех подходящих explicit VU корпуса. **Основной агрегат для H-тестов — невзвешенный** (по вопросам). Взвешенный приводится как анализ чувствительности.
- Проверка: таблица «страта × число доступных VU × выбрано».
- Пилотные 50 вопросов берутся из отдельной выборки VU (не пересекающейся с основной ни по VUID, ни по классу эквивалентности).

### Этап 3. Генерация вопросов (делает Claude Code)
- Единый промпт генерации с примерами фиксируется в `generation_log/`, вместе с версией модели и составом каждого батча.
- **Входы генератора** для каждого VU: текст VU, родительская секция (без VU-блоков), **все остальные explicit и implicit VU этой сущности и структур, на которые она ссылается** (`pNext`-цепочки, `*Info`-структуры параметров), секции из `refs`. Эталон должен выводиться только из поданного текста; знания вне него в эталон не добавляются.
- Батчами по ~25 VU генерируется для каждого VU:
  `{qid, vuid, equiv_class_id, stratum, style: identifier|descriptive, answer_type: rule|yes_no|scenario, question, reference_answer, expected_verdict?}`.
- **Парный дизайн по стилю (для H2)**: для **каждого** VU генерируются оба стиля, `identifier` и `descriptive`. Это даёт ~800 вопросов с ответом. Retrieval-фаза (дешёвая) считается на всех ~800. В генерацию и судейство (дорогие фазы) идёт один стиль на VU, выбранный случайно 50/50 со стратификацией по стратам. Если какой-то VU невозможно описать без идентификаторов, генератор помечает `descriptive_infeasible=true`. Такие VU исключаются из парного анализа H2, а доля таких VU по стратам идёт в отчёт.
  - `identifier`: можно упоминать имена API-сущностей, параметров, enum;
  - `descriptive`: без идентификаторов, описание ситуации обычными словами («when recording a draw call inside a render pass that…»).
- **`answer_type`** назначается кодом до генерации: целевое распределение rule 40% / yes_no 30% / scenario 30%, стратифицированно по стратам. Генератор может понизить тип до `rule` (см. ниже), понижение логируется.
- `gold_chunk_ids` **вычисляется кодом**, а не генератором: VU-чанки всего класса эквивалентности плюс части родительской секции.
- **`acceptable_vuids`** (множественный gold): после генерации каждый вопрос прогоняется через `rrf_rerank`. Для top-10 VU-чанков вне класса судья (отдельный вызов) проверяет: «отвечает ли этот VU на вопрос так же полно, как gold?». Утверждённые VU добавляются в `acceptable_vuids` и их классы в `gold_chunk_ids` с релевантностью 2. Вопросы, где таких VU > 2, помечаются как неоднозначные и идут на ручную проверку.
- Правила формулировки:
  - дословно цитировать VU нельзя, номера VUID и ссылки на них запрещены;
  - вопрос подразумевает однозначный ответ, проверяемый по одному VU (или его классу / `acceptable_vuids`);
  - `scenario`: нарушение должно быть одно. Генератор обязан явно проверить сценарий против **всех** поданных VU сущности и связанных структур и вернуть список проверенных VUID. Если это не удаётся обеспечить, тип меняется на `rule`;
  - `yes_no`: формулировки только вида «требуется ли / разрешено ли X при условии Y» (проверяемые по одному VU), а не «валиден ли весь сценарий». Ответы сбалансированы ~50/50 по «yes/no» внутри каждой страты.
- **Вопросы без ответа (~50)**, `stratum = unanswerable`, подтипы фиксируются заранее: несуществующая функция/структура/расширение (~20), ложная посылка о правиле (~20), ложная посылка о поведении существующей сущности (~10). Эталон: «такого нет / посылка неверна».
  - «Несуществующие» имена проверяются по объединению идентификаторов `vk.xml` всех тегов **и** текущего main Vulkan-Docs, а также по `aliases.json` и словарю SPIR-V.
  - Для ложных посылок о правилах генератор указывает, почему правила нет, со ссылкой на текст spec (VU или прозу главы, из которой следует обратное). Все 50 вопросов проверяются вручную.
  - Для судьи у unanswerable вместо текста VU подаётся обоснование отсутствия и, если есть, релевантный фрагмент spec.
  - Подтипы слишком малы для отдельных выводов: в отчёте по подтипам только описательная статистика.
- Автоматические фильтры:
  - максимальный общий n-gram с текстом VU ≤ 5 токенов (токенизация BM25-токенизатором без стемминга), кроме идентификаторов; считается в двух вариантах — без стоп-слов и со стоп-словами, отказ, если любой > 5 (§10);
  - нет дублей: cosine между вопросами (эмбеддер bge-m3, тот же, что в retrieval) выше порога. Порог калибруется на пилоте по распределению cosine заведомо разных и заведомо одинаковых пар (стартовое значение 0.92);
  - для `descriptive`: в вопросе нет идентификаторов. Идентификатором считается токен с префиксом `vk`/`Vk`/`VK_`, токен из camelCase/SNAKE_CASE из нескольких слов или токен из словаря SPIR-V. Однословные имена членов структур, совпадающие с обычными словами (`buffer`, `image`, `size`, `offset`, `flags`, `format`, `layout`, `stage`), не запрещаются;
  - проверка дрейфа стиля между батчами: распределение длины, типов и стилей по батчам.
- Ручная проверка: вы смотрите **80 пар (вопрос, эталон)**, стратифицированных по стратам, стилям и типам, и видите при этом все VU сущности. Брак — это любое из: неоднозначный вопрос, ответ зависит от нескольких VU, неверный эталон, утечка формулировки, второе нарушение в `scenario`. Если брака больше 10% (или верхняя граница 95% CI Уилсона больше 20%), правим правила и перегенерируем.
- Набор вопросов — неизменяемый артефакт: после утверждения он не перегенерируется, потому что вывод Claude Code не воспроизводим. Каждый вопрос хранит `question_hash`.
- Ограничение, которое войдёт в отчёт: вопросы написаны моделью семейства Claude. Поэтому Claude не используется ни как судья, ни как ответчик.
- Ограничение по внешней валидности: реальный пользователь validator assistant часто вставляет сообщение validation layer (там уже есть VUID) или код. Синтетические перефразы покрывают только один сценарий (см. бейзлайн `vuid_lookup` в Этапе 5).

### Этап 4. Индексы
- **BM25**: `bm25s` напрямую. Токенизатор свой: идентификаторы сохраняем целиком и дополнительно разбиваем camelCase и `SNAKE_CASE` на части (`vkCmdBindPipeline` → `vkcmdbindpipeline cmd bind pipeline`). Стоп-слова английские, стемминг только для не-идентификаторов. Идентификаторы в запросе расширяются алиасами из `aliases.json`. Параметры (k1, b) фиксируются в конфиге. Индексируется `index_text`.
- **Dense**: bge-m3 на GPU (fp16), эмбеддинги нормализованы, `IndexFlatIP` (точный поиск, корпус небольшой). Индекс строится один раз и сохраняется на диск. `max_length` эмбеддера задаётся явно. Во время построения Ollama выгружена.
- **Sparse (дешёвый дополнительный baseline)**: lexical weights из того же прохода bge-m3.
- В индекс идут обе гранулярности: секции (без VU-блоков) и VU-чанки.

### Этап 5. Retrieval-конфигурации

Основные (идут в генерацию):

| ID | Описание |
|---|---|
| `closed` | без контекста |
| `oracle` | gold VU-чанк этой сущности + часть родительской секции с `part_idx=0` |
| `oracle_distract` | gold (как в `oracle`) плюс 4 дистрактора: VU-чанки той же сущности или сущностей того же семейства команд (тот же префикс, например `vkCmdDraw*`, или тот же родительский раздел spec), **не входящие** в класс gold и в `acceptable_vuids`. Позиция gold в контексте случайная (seed) |
| `bm25` | BM25 top-k |
| `dense` | bge-m3 top-k |
| `rrf` | RRF(BM25 top-50, Dense top-50), k_rrf=60 |
| `rrf_rerank` | RRF top-50 → bge-reranker-v2-m3 → top-k |
| `rewrite_rrf_rerank` | qwen переписывает запрос (Vulkan-термины). Переписанный запрос **заменяет** исходный и в BM25, и в Dense → `rrf_rerank` |
| `hyde_rrf_rerank` | HyDE: гипотетический ответ qwen идёт в Dense, исходный запрос в BM25 → RRF → rerank (reranker получает исходный запрос) |

Только retrieval-метрики (дешёвая фаза B, без генерации): `sparse`, `bm25_rerank`, `dense_rerank`, `rrf_sparse` (BM25+Dense+Sparse), `rewrite_rrf`, `hyde_rrf`, `rewrite_append_rrf_rerank` (переписанный запрос **добавляется** к исходному, а не заменяет его). Эти конфигурации нужны, чтобы отделить вклад гибрида, rerank и трансформаций запроса.

Абляции чанкинга (только retrieval, на `rrf_rerank`): индекс только из VU-чанков; индекс только из секций; секции **вместе** с VU-блоками (без отдельных VU-чанков). Метрики для «только секции» считаются по мягкому Recall.

Дополнительные контрольные конфигурации генерации (на подвыборке 100 вопросов, разведочно):
- `oracle_entity`: все explicit VU сущности gold + `part_idx=0` секции. Отделяет ошибку «нашёл не ту сущность» от ошибки «не выбрал нужное правило»;
- `rrf_rerank_strict`: тот же контекст, промпт без разрешения опираться на собственные знания (см. Этап 6).

Тривиальные бейзлайны (без LLM, в отчёт): «всегда no» для `yes_no` (доля совпадения с `expected_verdict`); `vuid_lookup` — точный поиск по VUID в сообщении validation layer (иллюстрирует, что сценарий с вставленным сообщением решается тривиально и в эксперимент не входит).

Параметры:
- Глубина каждого подретривера ≥ 50, иначе RRF и rerank неявно урезаны.
- Retrieval-метрики считаем на `k ∈ {1, 3, 5, 10, 20}`.
- `k = 5` для генерации. На пилоте дополнительно проверяем `k ∈ {3, 10}` для `rrf_rerank`, чтобы увидеть, как k влияет на компромисс стоимости и точности (H5).
- **Сборка контекста** после retrieval:
  - дедупликация по `chunk_id`;
  - **дедупликация по классу эквивалентности**: из VU-чанков одного `equiv_class_id` в контексте остаётся один (с наивысшим рангом), освободившиеся места добираются следующими по рангу. То же для полностью совпадающего нормализованного текста;
  - если в top-k есть и VU-чанк, и часть его секции, оба остаются (секция в индексе без VU, так что текст не дублируется);
  - порядок — по рангу; в контекст LLM идёт `llm_text`.
- Логируем долю типов чанков (section / vu) в top-k по конфигурациям (проверка длинового смещения reranker).
- Логируем долю rewrite и HyDE, где появились идентификаторы, отсутствующие в объединении `identifiers.json`, `aliases.json` и словаря SPIR-V (галлюцинации трансформаций).
- Для `unanswerable` retrieval выполняется (контекст нужен для генерации), но retrieval-метрики не считаются. `oracle` и `oracle_distract` для `unanswerable` не запускаются (gold нет).

**Как уложиться в 8 GB VRAM: пайплайн по фазам с кэшированием.** Каждая фаза запускается **отдельным процессом**, чтобы гарантированно освободить CUDA-память.
1. Фаза A (только Ollama): rewrite и HyDE для всех вопросов → `runs/<id>/query_transforms.jsonl`.
2. Фаза B (только embedder и reranker, Ollama выгружена через `keep_alive=0`, освобождение VRAM проверено через `nvidia-smi`): retrieval по всем конфигурациям → `retrieved.jsonl`.
3. Фаза C (только Ollama и OpenRouter): генерация ответов.
4. Фаза D (OpenRouter): судейство.
5. Фаза L (отдельно, на подвыборке): замер задержки (см. Этап 6).

Все фазы идемпотентны. **Ключ кэша**:
- общий: `(qid, question_hash, config_id, model_id, repeat_idx, config_hash, prompt_hash, model_digest, corpus_hash)`, где `config_hash` включает k, глубины, параметры токенизатора, reranker, `num_ctx`, `num_predict`;
- для OpenRouter вместо `model_digest`: ID модели и закреплённый провайдер; фактические `model` и провайдер из ответа логируются, расхождение с ожидаемыми — ошибка;
- для генерации дополнительно: `retrieval_hash` (хэш списка `chunk_id` в собранном контексте);
- для судейства: `(answer_hash, judge_prompt_hash, judge_model_id, judge_repeat_idx)`;
- `repeat_idx` = 0 для основного прогона, 1–2 для повторов.

Запись в JSONL атомарная (через временный файл или построчный `fsync`), а при чтении обрезанная последняя строка отбрасывается. При перезапуске пайплайн продолжает с места остановки, а при изменении любого хэша пересчитывает зависимые фазы.

### Этап 6. Генерация ответов
- Ответчики: `qwen3.5:9b` (локально) и `answerer_remote` (OpenRouter, конфиг; сильная open-weights или frontier-модель не из семейства Claude, не Qwen и не из семейства судьи).
- Матрица (основной прогон): 2 модели × 9 конфигураций × ~400 вопросов с ответом + 2 модели × 7 конфигураций × ~50 unanswerable ≈ **7 900 ответов**. Локально ~3 950 ответов при 5–15 с на ответ занимают ~6–17 часов, запускать ночью. Плюс контрольные конфигурации и повторы (ниже).
- Единый системный промпт (английский):
  - «Answer concisely. Cite the VUID(s) your answer is based on, if any.»
  - Для RAG: «Use the provided context. If the context does not contain the answer, you may rely on your own knowledge, but say so explicitly. If you are not sure, answer "I don't know".»
  - Для `rrf_rerank_strict`: «Answer only from the provided context. If it does not contain the answer, answer "I don't know".»
  - Для closed-book та же инструкция без упоминания контекста.
- Лимит выходных токенов (`num_predict` / `max_tokens`) задан явно. Для reasoning-моделей `max_tokens` включает reasoning-токены с запасом. Ответ, обрезанный по лимиту (`finish_reason=length`, пустой контент), — ошибка вызова, повтор с увеличенным лимитом один раз, затем пропуск (см. политику пропусков).
- **Защита от обрезки контекста Ollama**: число токенов промпта считается **локально** токенизатором qwen с применённым шаблоном чата, и проверяется `prompt_tokens + num_predict ≤ num_ctx` до вызова. `prompt_eval_count` из ответа логируется, но не используется как критерий: при переиспользовании KV-кэша общего префикса в ряде версий Ollama он показывает только заново посчитанные токены (проверить поведение на своей версии).
- Для каждого вызова (rewrite, HyDE, embed, rerank, генерация, judge) логируем `phase, qid, config, model, repeat_idx, prompt_tokens, completion_tokens, reasoning_tokens, latency_s, provider, finish_reason, retries` в `runs/<id>/usage.jsonl`. Для вызовов OpenRouter добавляем ещё `cost_usd` и `cached_tokens`.
- Стоимость OpenRouter берём из `usage` в ответе API. Если её там нет, считаем по прайсу модели, который сохраняется в `manifest.json` на момент запуска, потому что цены меняются. Стоимость повторов после ошибок (429, сбой schema) учитывается отдельной строкой.
- Локальные вызовы (Ollama, embedder, reranker) в денежную стоимость не входят. Для них считаем только задержку.
- **Политика пропусков**: вызов с ошибкой повторяется до 3 раз с backoff. Если ответа всё равно нет (таймаут, пустой ответ, обрезка), ответ засчитывается как `incorrect`, `abstained=false`, с флагом `missing=true`. Доля `missing` по (модель × конфигурация) идёт в отчёт. Анализ чувствительности: с исключением `missing`.
- **Повторы**: на подвыборке 100 вопросов × {`closed`, `rrf_rerank`, `oracle`} ещё 2 прогона (`repeat_idx` 1–2; итого 3 с основным) на обе модели. Так оцениваем дисперсию (`temperature=0` на OpenRouter не гарантирует детерминизм).
- **Замер задержки (фаза L)**: отдельный прогон на 100 вопросах, по одному запросу (batch=1), после warm-up, загрузка моделей исключена. До пилота считается бюджет VRAM: qwen (квантизация + KV-кэш на `num_ctx`) + bge-m3 fp16 + reranker fp16 + занятое Windows. Если всё помещается — модели загружены одновременно. Если нет, сначала пробуем уменьшить `num_ctx`. Если и так не помещается, это фиксируется в отчёте, задержка считается суммой фаз с явной оговоркой, что цифры оптимистичны, а критерий задержки в H3 помечается как синтетический. Remote-задержку мерим в 2 разных времени суток.
- **Оценка бюджета** до пилота и уточнение после: число вызовов ответчика и судьи (correctness + faithfulness + проверка `acceptable_vuids` + повторы) × средние токены пилота × прайс. Лимит в конфиге и на ключе выставляется с запасом 30%.

### Этап 7. Оценка

#### 7.1 Retrieval
Метрики считаются по `gold_chunk_ids` (VU-чанки класса эквивалентности, классы `acceptable_vuids` и части родительской секции). Только для вопросов с ответом.
- Recall@k **строгий**: найден gold VU-чанк именно этой сущности.
- Recall@k **по классу** (основная метрика): найден любой VU-чанк того же класса эквивалентности или класса из `acceptable_vuids`.
- Recall@k **мягкий**: найдена любая часть родительской секции.
- MRR@10: релевантным считается чанк с градацией ≥ 2. nDCG@10 с градациями релевантности: gold VU = 3, VU того же класса или из `acceptable_vuids` = 2, часть родительской секции = 1, секции из `refs` = 1. Анкеры `refs` сопоставляются с чанками по карте «анкер → chunk_id», включая анкеры внутри частей секций.
- В отчёте приводится распределение размеров классов gold: при больших классах Recall@1 по классу тривиально завышается.
- Все метрики дополнительно в разрезе `style` (identifier / descriptive), это проверка H2. Сравнение стилей — **парное** (один VU, два стиля), только для VU без `descriptive_infeasible`.

#### 7.2 Генерация: LLM-judge
Судья — OpenRouter, модель из семейства, отличного от всех участников (§2), structured output (JSON schema), до 3 повторов при сбое. Доля сбоев логируется, после 3 сбоев применяется политика пропусков (Этап 6).
- **Ослепление**: судья не знает модель и конфигурацию. Перед подачей судье из ответа маскируются маркеры конфигурации («according to the provided context», «the context does not mention» и т. п., по списку регулярок) и номера VUID (VUID проверяются отдельно автоматически). Порядок вызовов перемешан.
- **Correctness** оценивается **одинаково во всех конфигурациях, без поданного контекста**. На входе: вопрос, эталонный ответ, текст VU, тексты VU из `acceptable_vuids` и **один** представитель класса (класс дедуплицирован по тексту), ответ модели.
  - `correctness ∈ {correct, partial, incorrect}`;
  - `abstained: bool`;
  - `hallucination: bool` в узком смысле: утверждение, противоречащее поданному VU или эталону. Существование идентификаторов судья **не** оценивает, это делает автопроверка;
  - короткое обоснование.
- Правила рубрики:
  - отказ («I don't know») → `abstained=true`, `correctness=incorrect` для вопросов с ответом и `correct` для `unanswerable`;
  - отказ с догадкой («not sure, but probably X») → `abstained=false`, оценивается X;
  - верный ответ плюс ложное утверждение → `partial`, `hallucination=true`;
  - в `scenario` засчитывается целевое нарушение. Если модель назвала другое реальное нарушение, которого не должно быть по построению вопроса, это `partial`, и вопрос попадает в разбор (возможный брак вопроса);
  - для `unanswerable`: `correct`, если модель отвергла посылку или сказала, что сущности нет; согласие с ложной посылкой → `incorrect`, `hallucination=true`.
- **Faithfulness** (только RAG, отдельный вызов судьи): ответ опирается на поданный контекст, а не противоречит ему. Ответ из собственных знаний модели помечается отдельно (`self_knowledge=true`), в том числе когда модель сама об этом заявила.
- **Автоматические проверки** (без судьи):
  - идентификаторы в ответе сверяются с объединением `identifiers.json` (все исторические теги), `aliases.json` и словаря SPIR-V/GLSL. Несуществующие → `fabricated_identifier=true`. Идентификаторы, существующие только в старых тегах, помечаются отдельно (`outdated_identifier`);
  - процитированные VUID сверяются с `validusage.json` текущего тега: несуществующий VUID → `fabricated_vuid=true`;
  - citation accuracy: процитированный VUID ∈ класс gold или `acceptable_vuids`. Считается отдельно для closed-book и RAG (в RAG VUID есть в `llm_text`, поэтому метрики несравнимы напрямую);
  - для `yes_no` вердикт извлекается из ответа (`yes | no | conditional | none`) и сравнивается с `expected_verdict`. Это дополнительная проверка судьи; доля `conditional` идёт в отчёт.
- Score: correct=1, partial=0.5, incorrect=0.
- **Selective accuracy**: точность среди ответов без отказа и доля отказов (coverage) по (модель × конфигурация). Нужна, чтобы отличать модель, которая честно отказывается, от модели, которая ошибается.
- **Калибровка судьи**: вы размечаете 80 ответов, стратифицированных по модели, конфигурации, страте и `answer_type` (не по метке судьи). Разметка **слепая**: вы не видите ни вывод судьи, ни модель, ни конфигурацию. 40 используются для настройки рубрики, 40 — отложенная выборка для финального κ.
  - correctness: взвешенный (linear) Cohen's κ; abstained и hallucination: обычный κ. Все κ с bootstrap 95% CI (на 40 элементах CI порядка ±0.2, это указывается в отчёте).
  - Цель κ ≥ 0.6 на отложенной выборке, иначе правим рубрику и размечаем новую отложенную выборку.
  - Ограничение: разметку делает один человек; уровень экспертизы в Vulkan указывается в отчёте.
  - Оценка трудозатрат на ручную работу (80 пар вопросов, 50 unanswerable, 80+ ответов, неоднозначные `acceptable_vuids`, разбор ошибок) фиксируется до пилота.
- **Смещения судьи**: корреляция score с длиной ответа внутри (модель × конфигурация). Если |ρ| > 0.3, на 40 размеченных ответах проверяем, есть ли такая же корреляция в ручной разметке. Если у человека её нет, это смещение судьи: правим рубрику (явное указание не поощрять длину) и перепроверяем κ.

#### 7.3 Стоимость (только OpenRouter) и задержка
- Стоимость ответа `answerer_remote` = стоимость его генерации, включая reasoning-токены. Rewrite, HyDE, retrieval и rerank выполняются локально и в стоимость не входят. Затраты на судью считаются отдельно: это цена эксперимента, а не системы.
- Если провайдер применял prompt caching, стоимость считается как фактическая и отдельно без кэша.
- Метрики `answerer_remote` по конфигурациям:
  - `cost_per_question`, а также средние входные, выходные и **reasoning**-токены отдельно (closed-book может «думать» дольше, это отдельный механизм изменения стоимости для H5);
  - `cost_per_correct = суммарная стоимость / сумма score` **по всем вопросам с ответом** (не по стратам: в closed на recent сумма score близка к нулю). По стратам приводится только с bootstrap CI и пометкой, если сумма score < 5;
  - прирост score на каждый $ относительно `closed`.
- Парето-фронт «score против стоимости» для `answerer_remote`.
- Задержка p50/p95 из фазы L для обеих моделей и всех конфигураций.

#### 7.4 Статистика
- **Кластерный парный bootstrap** 95% CI по сущностям (до 3 вопросов на сущность зависимы): ресэмплируются сущности, и для каждой выбранной сущности берутся её вопросы **во всех конфигурациях одновременно**. 10 000 ресэмплов. Для всех метрик и разниц.
- Парные сравнения конфигураций — **кластерный paired permutation test** (перестановка меток конфигураций внутри вопроса, с сохранением кластеров по сущностям):
  - для бинарной корректности: `correct` = 1, остальное = 0. Вариант «partial = 1» как анализ чувствительности. McNemar приводится только как справочный (он предполагает независимость);
  - для score.
- Non-inferiority (H4): односторонний тест, нижняя граница кластерного bootstrap CI.
- Поправка Holm **только внутри семейства основных сравнений** (§7.5). Размер семейства фиксируется заранее (см. таблицу). Всё остальное — разведочный анализ без претензии на значимость.
- **Мощность**: перед полным прогоном по пилоту оцениваем долю расхождений (discordant pairs) и межкластерную корреляцию и считаем MDE **для парной разницы** с учётом кластеров. Для H4 отдельно: вероятность подтвердить NI при истинной разнице 0 с маржой −5 п.п. Если мощность < 0.8, до полного прогона либо увеличиваем выборку, либо пересматриваем маржу, либо переводим гипотезу в разведочные (фиксируется в §7.5 до прогона).
- Основной агрегат — невзвешенный; взвешенный по стратам — анализ чувствительности (Этап 2).
- Разрезы: конфигурация × страта × модель × стиль × answer_type × entity_kind.

#### 7.5 Основные сравнения и критерии гипотез (фиксируются до полного прогона)
Семейство Holm: H1a, H1b, H2a, H2b, H3a, H3b, H4, H5 — **8 тестов**. Остальное разведочно.

| Тест | Сравнение | Критерий подтверждения |
|---|---|---|
| H1a | qwen: `rrf_rerank` vs `closed`, вопросы с ответом | score выше, p_Holm < 0.05 |
| H1b | remote: `rrf_rerank` vs `closed`, вопросы с ответом | score выше, p_Holm < 0.05 |
| H1 (разведочно) | разница `rrf_rerank − closed` на `recent` + `ext_niche` против `core_1_0` | CI разницы разниц не содержит 0. MDE для DiD при 160 против 80 вопросов ~15–20 п.п., поэтому вне семейства Holm |
| H2a | `rrf` vs `bm25` по Recall@5 (класс), все вопросы с ответом обоих стилей | `rrf` значимо лучше, p_Holm < 0.05 |
| H2b | `rrf` vs `dense` по Recall@5 (класс) | `rrf` значимо лучше, p_Holm < 0.05 |
| H2 (разведочно) | взаимодействие «конфигурация × стиль» на парных вопросах | преимущество `rrf` над `bm25` на `descriptive` больше, чем на `identifier` (CI разницы разниц не содержит 0) |
| H3a | `rrf_rerank` vs `rrf` по Recall@5 (класс) | +≥ 5 п.п. и p_Holm < 0.05 |
| H3b | `rrf_rerank` vs `rrf` по score (обе модели вместе, страта по модели) | score значимо выше, p_Holm < 0.05; дополнительное условие (не тест): прирост p50 задержки ≤ 0.5 с, с пометкой, если задержка синтетическая (Этап 6) |
| H4 | qwen `rrf_rerank` vs remote `closed` | non-inferiority: нижняя граница 95% CI (qwen − remote) > −5 п.п. (маржа пересматривается по расчёту мощности до прогона) |
| H5 | remote `rrf_rerank` vs remote `closed` | `cost_per_question` выше и `cost_per_correct` ниже (CI обеих разниц не содержат 0); в Holm входит p для `cost_per_correct` |

`oracle` используется как верхняя граница генерации при идеальном контексте (не обязательно 100%): разница `oracle − rrf_rerank` показывает, сколько теряется на retrieval. `oracle_entity − oracle` показывает потери на выборе правила внутри сущности.

1. Этапы 0–2: сборка spec, корпус, VU, классы эквивалентности и страты. Проверка: покрытие ≥ 99%, расхождения с Headers разобраны, таблица страт, 10 случайных чанков каждого типа глазами, 10 крупнейших классов эквивалентности глазами, unit-тесты токенизатора, нормализации и парсера условий проходят, бюджет VRAM для фазы L посчитан, оценка бюджета OpenRouter и трудозатрат сделана.
2. Этап 3, **пилот на 50 вопросах** из отдельной выборки VU (включая 5 `unanswerable` и оба стиля). Проверка: вы ревьюите вопросы и эталоны; калибруется порог cosine для дедупликации.
3. Этапы 4–5 на пилоте. Проверка: Recall@k выглядит разумно, `oracle` даёт 100% строгого Recall, токенизатор BM25 работает, нет обрезки контекста Ollama (по локальному подсчёту), thinking выключен, дедупликация по классу работает.
4. Этапы 6–7 на пилоте. Проверка:
   - калибровка судьи (κ на отложенной выборке);
   - экстраполяция времени полного прогона и расходов OpenRouter (ответчик и судья отдельно), бюджетный лимит в конфиге и на ключе;
   - расчёт мощности (парные разницы с кластерами, NI для H4); **фиксация §7.5** (основные сравнения, размер семейства, пороги и маржи) до полного прогона.
5. Генерация основных ~400 VU (оба стиля), проверка `acceptable_vuids`, ~45 `unanswerable`, ручная проверка 80 пар, полный прогон. Пилотные вопросы в подтверждающий анализ не входят.
6. Этап 8: отчёт.

## 6. Риски
| Риск | Митигация |
|---|---|
| Не хватает VRAM (qwen 9B + KV-кэш + embedder + reranker + Windows) | фазы отдельными процессами с выгрузкой моделей и проверкой `nvidia-smi`; уменьшение `num_ctx`; reranker в fp16 или на CPU (оценить заранее: ~110k пар на CPU — часы) |
| Сборка spec на Windows | Docker-образ Khronos с фиксированным digest через WSL, репозиторий в ext4; fallback — разбор сырого adoc с обработкой `ifdef` и `include` |
| Шаблоны `commonvalidity` дают одинаковые VU у разных команд | классы эквивалентности, не больше одного VU на класс в выборке, Recall по классу, дедупликация по классу в контексте |
| Gold шире класса эквивалентности | `acceptable_vuids`, проверка судьёй и ручной разбор неоднозначных |
| Сценарий нарушает ещё один VU | генератор видит все VU сущности и связанных структур; `yes_no` только про одно требование |
| BM25 выигрывает за счёт утечки слов из вопроса | n-gram фильтр, перефразирование, стиль `descriptive` |
| Эффект стиля смешан с VU | парный дизайн: оба стиля для каждого VU |
| Судья пристрастен к модели своего семейства | судья из семейства, отличного от всех участников, слепое судейство, калибровка по ручной разметке с отложенной выборкой |
| Судья не может проверить утверждения вне поданного VU | узкое определение галлюцинации, автопроверка идентификаторов и VUID |
| Ложные срабатывания проверки идентификаторов (SPIR-V, алиасы, старые имена) | объединение исторических `vk.xml`, `aliases.json`, словарь SPIR-V, отдельный флаг `outdated_identifier` |
| OpenRouter меняет провайдера или квантизацию | `provider.order`, `allow_fallbacks: false`, `require_parameters: true`, логирование фактического провайдера и модели |
| Провайдер OpenRouter недоступен при `allow_fallbacks: false` | возобновляемый пайплайн, ожидание; смена провайдера только между фазами с записью в manifest |
| Ollama молча обрезает промпт | `num_ctx` в каждом запросе, локальный подсчёт токенов до вызова |
| Устаревший кэш после правок | хэши вопроса, промпта, конфига, модели, корпуса, retrieval и `repeat_idx` в ключе кэша |
| Нестабильные `chunk_id` после пересборки корпуса | детерминированные `chunk_id` из анкера, `part_idx` и хэша текста |
| LlamaIndex скрывает поведение (подмешивание метаданных в текст, дефолтный `Settings.llm` = OpenAI, `use_async` и event loop на Windows, устаревший `tokenizer` в BM25Retriever) | ядро retrieval пишем сами; если LlamaIndex используется, явно задаются `excluded_*_metadata_keys`, `llm`, `use_async=False` |
| Долгая локальная генерация | кэш и возобновление прогона, пилот перед полным запуском |
| Thinking-режим qwen3.5 раздувает задержку | `think=false` и проверка отсутствия `<think>` в ответах; при желании отдельная ось эксперимента |
| Модель отвечает по старой версии spec | флаг `text_changed_recently`, `outdated_identifier`, отдельный разбор |
| Не хватает VU в страте | берём все доступные, веса страт в анализе чувствительности |
| Недостаточная мощность (DiD для H1, NI для H4) | расчёт мощности на пилоте, DiD вынесен в разведочные, маржа H4 пересматривается до прогона |
| Пилот загрязняет подтверждающую выборку | пилот из отдельной выборки VU, в confirmatory-анализ не входит |
| Троттлинг ноутбука искажает задержку | фиксированный режим питания, работа от сети, warm-up |
| Утечка eval-сета в обучающие данные провайдеров | `data_collection: deny` |

### 9.2 Разрешение противоречий

1. **Источник `validusage.json` для датирования (Этап 2).** Для исторических тегов используется `registry/validusage.json` из Vulkan-Headers того же тега (без Docker-сборки на каждый тег). Для текущего тега источник истины — Docker-сборка (§2), а Headers-версия — санити-чек; если на текущем теге наборы VUID расходятся больше чем на 0.5%, датирование по Headers считается ненадёжным и для исторических тегов делается Docker-сборка. Если для какого-то тега нет файла в Headers, он пропускается, а пропуск пишется в `vuid_history.json`.
2. **Число unanswerable.** Основной набор — **50** (20/20/10 по подтипам), пилот — **дополнительные 5**, не пересекающиеся с основными. Строка «~45 `unanswerable`» в §5 п.5 заменяется на 50.
3. **Порядок этапов.** Этап 3 делится на **3a** (генерация вопросов, фильтры, ручная проверка) и **3b** (`acceptable_vuids`, после построения индексов Этапа 4). `gold_chunk_ids` окончательно фиксируется после 3b, retrieval-метрики считаются только по окончательному `gold_chunk_ids`.
4. **Кластерный перестановочный тест.** Перестановка делается **на уровне кластера**: для каждой сущности с вероятностью 1/2 метки двух сравниваемых конфигураций меняются местами **у всех её вопросов одновременно** (эквивалентно sign-flip теста на суммах парных разниц по кластерам). 10 000 перестановок, двусторонний p (односторонний для H4 — там bootstrap, не перестановка). В H3b кластер — сущность вместе с вопросами обеих моделей (страта по модели — внутри кластера). В H4 сравниваются разные модели на одних и тех же вопросах, пары — по `qid`.

### 9.3 Недостающие спецификации

#### Отнесение VU к страте (Этап 2)
Входы: условие VU в ДНФ (из adoc, Этап 1 п. 4а; клауза — множество `VK_VERSION_x_y` и расширений, подфичи `VK_{BASE,COMPUTE,GRAPHICS}_VERSION_x_y` уже сведены к `VK_VERSION_x_y`), происхождение сущности (`core_version` или `extension`, с `promotedto`; `registry.json`), данные gpuinfo. Условие `core` означает, что VU не окружён `ifdef` (520 VU), `VK_VERSION_1_0` — окружён только `ifdef` версии 1.0 (1 263 VU); оба трактуются как п. 2.

1. Если дата VU позже cutoff → `recent` (дальше вычисляется «базовая страта» только для разреза `recent × происхождение`).
2. Если условие `core` → путь доступа = происхождение сущности: core-версия сущности (с учётом того, что сущность объявлена в `<feature>` — например, `vkCmdBeginRendering` объявлена в 1.3) или её расширение.
3. Иначе для каждой клаузы определяется путь доступа:
   - клауза только из `VK_VERSION_*` → core, версия = max(версия клаузы, core-версия сущности);
   - клауза содержит расширения; если **все** они имеют `promotedto` core-версию → core, версия = max(promotedto), флаг `cond_ext_only_promoted=true`;
   - иначе → «расширения клаузы» (не-promoted).
4. Если хотя бы одна клауза даёт core → берётся core-путь с минимальной версией: 1.0 → `core_1_0`, 1.1–1.4 → `core_promoted`.
5. Иначе для каждой клаузы популярность = min покрытия её расширений (vendor-расширение = 0), берётся клауза с максимальной популярностью: ≥ порога и все расширения KHR/EXT → `ext_popular`, иначе `ext_niche`.
6. Условие не распарсилось или ссылается на неизвестное имя → VU исключается из вопросов, логируется.

Примеры (покрываются тестами): `vkCmdDraw` + `core` → `core_1_0`; `vkCmdDraw` + `VK_VERSION_1_3,VK_KHR_dynamic_rendering` → `core_promoted`; `vkCmdDraw` + `VK_EXT_shader_object` → `ext_*` по покрытию; `vkCmdDrawMeshTasksEXT` + `core` → `ext_*` по покрытию `VK_EXT_mesh_shader`; `vkCmdDraw` + `VK_NV_…` → `ext_niche`.

#### Алгоритм выборки VU (Этап 2)
1. Кандидаты фильтруются (исключения Этапа 2) и сортируются по `(stratum, entity, vuid)`.
2. Страты обходятся в порядке возрастания числа кандидатов (редкие первыми, чтобы им хватило сущностей и классов).
3. Внутри страты — перемешивание `random.Random(seed + hash(stratum))` и жадный проход: VU принимается, если у сущности < 3 принятых VU (глобально по всем стратам) и его класс эквивалентности ещё не использован.
4. Основная выборка строится первой; пилотная — тем же алгоритмом из остатка, исключая все VUID и классы эквивалентности основной выборки; цель пилота 45 VU с ответом, пропорционально стратам.

#### Генерация вопросов силами Claude Code (Этап 3a)
- `vkrag questions prepare --sample main|pilot` пишет `generation_log/batches/<sample>/batch_NNN.input.json` (батч = группа сущностей, упаковка по объёму контекста, §10) и `generation_log/<sample>_assignments.json`: для каждого VU — текст, родительская секция, все VU сущности и связанных структур, секции из `refs`, назначенный кодом `answer_type`, `expected_verdict` (для `yes_no`, назначается кодом 50/50 внутри страты) и `qid` для обоих стилей.
- Промпт генератора — `generation_log/prompt_v1.md` (версионируется; смена версии — только до утверждения набора).
- Claude Code обрабатывает батч в **отдельном субагенте с чистым контекстом** (чтобы не накапливался контекст и не было дрейфа; решение §10) и пишет `batch_NNN.output.jsonl` строго по схеме: `{qid, vuid, style, answer_type, question, reference_answer, expected_verdict?, descriptive_infeasible, downgraded_to_rule?, verdict_changed?, checked_entities: [...], checked_vuids: [...], also_relevant_vuids: [], notes?}`.
- Если вопрос с назначенным `expected_verdict` построить нельзя, генератор меняет вердикт и ставит `verdict_changed=true`; после всех батчей `prepare` подбирает дополнительные VU для восстановления баланса 50/50 в страте.
- `vkrag questions validate` проверяет схему, `checked_entities` ∪ `checked_vuids` ⊇ VU сущности (для `scenario` — и связанных структур), пустой `also_relevant_vuids`, n-gram фильтр, запрет идентификаторов для `descriptive`, дубли (cosine), считает `question_hash`. Отклонённые вопросы уходят в `batch_NNN.rejects.jsonl` с причиной и перегенерируются в новом батче.
- Unanswerable: отдельный вход `batch_unans.input.json` (квоты подтипов, списки существующих имён для проверки), выход с обязательным `rationale` и `spec_evidence`.

#### Промпты (черновики, финальные тексты — в `src/vkrag/generation/prompts/*.md`, хэш идёт в ключ кэша)
- **Ответчик, системный (RAG):** «You are an expert on the Vulkan API specification. Answer concisely. Cite the VUID(s) your answer is based on, if any. Use the provided context. If the context does not contain the answer, you may rely on your own knowledge, but say so explicitly. If you are not sure, answer "I don't know".» Closed-book — без двух предложений о контексте; `strict` — как в Этапе 6.
- **Формат контекста:** блок `Context:`, далее элементы `[n] (VU | Section: <title>)\n<llm_text>`, разделитель `\n---\n`, затем `Question: <question>`. Для `yes_no` добавляется «Start your answer with Yes or No.»
- **Rewrite:** «Rewrite the user's question as a search query for the Vulkan specification. Use precise Vulkan terminology (command, structure, enum and feature names) where you are confident they exist. Output only the query, one line.»
- **HyDE:** «Write a short passage (3–5 sentences) in the style of the Vulkan specification's Valid Usage section that would answer the question. Output only the passage.»
- **Судья, correctness:** роль эксперта Vulkan; вход — вопрос, эталон, текст gold VU, VU из `acceptable_vuids`, один представитель класса, замаскированный ответ; явные правила рубрики §7.2 и указание «Do not reward length or extra detail; judge only whether the answer's claims match the reference.» Выход — схема ниже.
- **Судья, faithfulness:** вход — поданный контекст и ответ (без эталона); вопрос «supported / contradicts / not grounded» и флаг `self_knowledge`.
- **Судья, проверка `acceptable_vuids`:** вход — вопрос, эталон, gold VU, кандидат VU; вопрос «Does the candidate rule answer the question as fully and correctly as the gold rule?» → `{equivalent: bool, reason}`.

JSON schema судьи (correctness):
```json
{"correctness": "correct|partial|incorrect", "abstained": false,
 "hallucination": false, "scenario_other_violation": false, "reason": "≤ 60 words"}
```
Faithfulness: `{"faithfulness": "supported|contradicts|not_grounded", "self_knowledge": false, "reason": "..."}`. Все поля обязательные, `additionalProperties: false`.

#### Маскировка ответа перед судьёй
Регулярки (регистронезависимо), заменяются на пустую строку или `[VUID]`: `\bVUID-[A-Za-z0-9_-]+\b`; `\b(according to|based on|per|as stated in|from) the (provided |given )?(context|documents?|excerpts?|passages?)\b[^.,;]*`; `\bthe (provided |given )?(context|documents?|excerpts?) (does not|doesn't) (mention|contain|say|cover)[^.]*\.`; `\b(context|passage|excerpt|chunk) \[?\d+\]?`; `\[\d+\]`; `\bfrom (my|general) (own )?knowledge\b[^.]*`. Список хранится в `eval/masking.py` с тестами; доля ответов, где маскировка сработала, логируется по конфигурациям.

#### `oracle_distract`: нехватка дистракторов
Порядок добора: (1) VU той же сущности; (2) VU сущностей того же префикса семейства; (3) VU того же родительского раздела spec; (4) ближайшие по dense-сходству VU-чанки к gold среди остальных. Все — вне класса gold и `acceptable_vuids`. Уровень добора логируется; если ни на одном уровне не набралось 4, используется сколько есть, флаг `distractors_short`.

#### Ручная разметка
- `vkrag annotate export --task {question_review|unanswerable_review|judge_calibration|acceptable_ambiguous}` пишет CSV (UTF-8 с BOM для Excel) с непрозрачными `item_id`, перемешанным порядком и только теми колонками, которые должен видеть разметчик; ключ (`item_id → qid, model, config, judge_output`) — в отдельном `*.key.jsonl`, который разметчик не открывает.
- Колонки ответа: выпадающие значения задаются в заголовке (например, `correctness[correct|partial|incorrect]`), плюс `comment`.
- `vkrag annotate import` валидирует значения и сливает с ключом. Для калибровки судьи split 40/40 делается кодом до экспорта (seed), во второй файл попадает только отложенная выборка.

#### Расчёт мощности (§7.4)
Симуляционный: из пилота берутся оценки по кластерам (доля discordant pairs, ICC); 2 000 симуляций выборки размера основного прогона, ресэмплинг сущностей пилота с подмешанным эффектом Δ (сдвиг вероятности correct у одной конфигурации). MDE — минимальный Δ с шагом 1 п.п., при котором кластерный перестановочный тест отвергает H0 на уровне α = 0.05/8 (консервативный худший случай Holm) в ≥ 80% симуляций. Для H4 — доля симуляций при истинной разнице 0, где нижняя граница кластерного bootstrap CI > −маржа. Скрипт `vkrag power`.
